etf_selection: what the code does and how the pieces fit

A structural tour of the repository: the data flow from raw market bars to a recommended ETF basket with weights, the modules that carry each step, the settings that change the answer, and the traps worth knowing about.

How to use this

Sections follow the order the data moves, not the order the files sit on disk. Code snippets are copied unedited from the files named in each heading. Every number in a Sample data box came from running this repository's own code on its own data on 2026-08-10; nothing is estimated. Coloured boxes flag design choices, traps and weaknesses.

The process in plain English

The project answers one question: given every liquid US-listed exchange-traded fund (ETF — a fund whose shares trade on an exchange like a stock), which thirty of them should you hold, and in what proportions? It first keeps the 500 most heavily traded ETFs, then keeps only those with a full eight years of history and a decent return, then picks a spread-out subset using rank correlations between their daily returns, then runs seven different textbook rules for turning that basket into weights, and finally checks what buying and holding those weights would have been worth.

What it does

Input: the 500 tickers from stage 1. Output: data/raw/daily_close_volume_screened_2016_2025.parquet, 1,081,660 rows and four columns, 500 tickers, 2016-01-04 to 2025-12-31, 11.22 MB on disk. Role: the shared offline data file; four of the six code areas read it and nothing else.

Why argMax(close, ts) and not "the 16:00 bar"

argMax(close, ts) means "the close value belonging to the row with the largest ts". Minute bars only exist when a trade happened, so an illiquid ETF may have no bar in the final minute of the session. Asking for the last bar that exists gives the true last traded price of the day; asking for a fixed timestamp would return nothing on those days.

Trap

exclusive_end_date() turns an inclusive date such as 2025-12-31 into the exclusive bound 2026-01-01. Without it, ts <= '2025-12-31' would be read as ts <= '2025-12-31 00:00:00' and silently drop the whole last trading day. Timestamps compared against bare dates are a classic off-by-one-day bug.

Why the file is validated after writing

_validate_parquet_magic() reads the first four bytes and the last four bytes and insists both are PAR1. Parquet files begin and end with that marker, so a truncated download fails loudly at export time rather than three stages later as a confusing pandas error.

In plain words

Turn a long list of prices into a grid with dates down the side and tickers across the top, drop any ticker with too many missing days, and convert prices into day-to-day returns.

The formula

$$r_{i,t}=\ln\!\left(\frac{P_{i,t}}{P_{i,t-1}}\right),\qquad \text{coverage}_i=\frac{\#\{t: P_{i,t}\ \text{observed}\}}{T}$$

$P_{i,t}$ is the closing price of ETF $i$ on sampled date $t$; $r_{i,t}$ is its log return, meaning the natural logarithm of the price ratio; $T$ is the number of sampled dates in the window. A ticker is kept when $\text{coverage}_i \ge 0.80$.

Why log returns rather than percentage changes

Log returns add up across time: the return over eight years is simply the sum of the daily values, with no compounding arithmetic. That single property is used in four separate places here — the total-return hurdle, the average-calendar-year hurdle, the cumulative wealth path, and the drawdown calculation. Converting back to a percentage is $e^{\sum_t r_t}-1$.

05Stage 3 — the survivor filters

apply_shared_selection_filters() — four hurdles in a fixed order

The filters run in this sequence, and each one re-checks that the anchor tickers survived:

  1. Manual blacklist — names you name explicitly. Raises if you blacklist an anchor.
  2. Total-return hurdle — cumulative log return over the whole window must be at least MIN_SELECTION_TOTAL_RETURN.
  3. Average calendar-year hurdle — optional; only applied when the caller passes a number.
  4. Volatility band — annualised volatility must lie between MIN_ANN_VOL and MAX_ANN_VOL. Anchors are re-added even if they fail.
The formula

$$R_i=\sum_{t=1}^{T} r_{i,t}\;\ge\;\theta,\qquad \bar{A}_i=\frac{1}{Y}\sum_{y=1}^{Y}\ \sum_{t\in y} r_{i,t}\;\ge\;\alpha,\qquad \sigma_i=\mathrm{sd}(r_{i,\cdot})\sqrt{k}\in[\sigma_{\min},\sigma_{\max}]$$

$R_i$ is ETF $i$'s cumulative log return over the whole window and $\theta$ is MIN_SELECTION_TOTAL_RETURN $=0.1823$. $Y$ is the number of calendar years in the sample and $\bar{A}_i$ is the average of the yearly log-return sums, compared against the hurdle $\alpha$. $\mathrm{sd}$ is the sample standard deviation with one degree of freedom removed, $k$ is the number of return periods per year (252 for daily, 52 for weekly), and $[\sigma_{\min},\sigma_{\max}]=[0.10,0.60]$.

Why a volatility band and not a name blacklist

Leveraged and inverse ETFs do not identify themselves in the data. A ceiling of 60 % annualised volatility catches them mechanically, and a floor of 10 % removes money-market substitutes whose returns would otherwise look like free Sharpe ratio. The band replaces a list that would go stale every time a new product launches.

The weakness, stated honestly

The total-return hurdle keeps only ETFs that went up over exactly the window that is later used to score and backtest them. This is in-sample selection: nothing here could have been known on 2018-01-01. It is the largest single reason the backtest numbers in section 10 should not be read as an expectation of future performance.

06Stage 4 — correlation and distance

compute_spearman_corr()

filled = log_ret.fillna(log_ret.median())

What it does

Input: the 2,011 by 233 return panel. Output: a 233 by 233 symmetric matrix of Spearman rank correlations. Role: the raw material for every selector and for HRP.

Why rank correlation rather than ordinary correlation

Spearman correlation is Pearson correlation applied to the ranks of the observations rather than the values. Daily ETF returns have fat tails: one crash day can dominate an ordinary correlation between two funds that are otherwise unrelated. Ranking caps the influence of any single day at one rank position, and it also picks up relationships that are consistent but not straight-line.

compute_distance_matrix() — the signed distance

The formula

$$D_{ij}=\sqrt{\tfrac{1}{2}\left(1-r_{ij}\right)}$$

$r_{ij}$ is the Spearman correlation between ETFs $i$ and $j$; $D_{ij}$ is the distance between them. The identity behind it: if $a$ and $b$ are unit-length vectors with $a\cdot b=r$, then $\|a-b\|^{2}=a\cdot a-2a\cdot b+b\cdot b=2(1-r)$, so $\|a-b\|=\sqrt{2(1-r)}$ and dividing by $\sqrt{2}$ scales the result onto $[0,1]$.

Why signed and not absolute distance

The obvious alternative, $D = 1-|r|$, would place a bond fund with $r=-0.8$ against equities at distance 0.2 — treating it as nearly the same asset. That is backwards. A negatively correlated holding is the most useful diversifier there is, and the signed formula puts it at the far end of the space where it belongs.

select_by_greedy() — furthest-first traversal

min_dist_masked = min_dist.copy()
min_dist_masked[selected_idx] = -np.inf
best_val = min_dist_masked.max()
...
selected_idx.append(next_idx)
# For each remaining candidate c, min_dist[c] may decrease now that
#   new_min_dist[c] = min(min_dist[c], D[c, next_idx])
min_dist = np.minimum(min_dist, D[:, next_idx])
The formula

$$\text{next}=\arg\max_{c\notin S}\ \min_{s\in S} D(c,s)$$

$S$ is the set already selected, $c$ runs over the candidates not yet chosen, and $D$ is the signed distance matrix. In words: for every candidate work out how close it is to its nearest current holding, then take the candidate whose nearest holding is furthest away.

Why the running min_dist vector matters

Recomputing $\min_{s\in S} D(c,s)$ from scratch each step would cost $O(n \cdot |S|)$ every step. Because adding one name can only ever reduce a candidate's nearest-holding distance, one elementwise minimum against the new column is enough. Each step becomes $O(n)$. This is the standard furthest-first update, and the source comment calls it "the key efficiency trick".

Trap

select_by_maxdiv() — greedy on a portfolio-level objective

The formula

$$DR(w)=\frac{w^{\top}\sigma}{\sqrt{w^{\top}\Sigma w}},\qquad DR_{\text{EW}}=\frac{\frac{1}{N}\sum_{i=1}^{N}\sigma_i}{\sqrt{\frac{1}{N^{2}}\mathbf{1}^{\top}\Sigma\mathbf{1}}}$$

$w$ is the weight vector, $\sigma$ the vector of individual volatilities with $\sigma_i=\sqrt{\Sigma_{ii}}$, and $\Sigma$ the covariance matrix of the daily log returns. $N$ is the number of holdings and $\mathbf{1}$ a vector of ones, so $w=\mathbf{1}/N$ is equal weighting. $DR=1$ means no diversification benefit at all; higher is better. The measure is from Choueifaty and Coignard (2008).

In plain words

At each step it asks "if I added this fund to what I already hold, and split money evenly, how much would the portfolio's total risk fall below the average risk of its parts?" and takes the winner.

Seven rules live in src/portfolio_allocation/, one file each, all registered in STRATEGY_FUNCTIONS. Six of them are the same optimisation with a different objective function; only HRP is structurally different.

Why one shell and seven objectives

Five of the seven rules are the same problem — long-only, fully invested, capped per holding — with a different scalar to minimise. Putting the bounds, the sum-to-one constraint, the starting point and the convergence warning in one place means a change to the constraint set cannot apply to some rules and not others. Only min_cvar opts out, because it optimises over an extra variable, and only hrp does not optimise at all.

Trap

warn_if_not_converged only prints. A failed optimisation still returns result.x, which is whatever the solver reached when it gave up, and the caller has no way to tell without reading the console. In a notebook, that warning scrolls past.

min_cvar() — the one with an extra variable

The formula

$$\min_{w,\zeta}\ \ \zeta+\frac{1}{T(1-\alpha)}\sum_{t=1}^{T}\max\!\left(-r_t^{\top}w-\zeta,\ 0\right)$$

$r_t$ is the vector of asset log returns on day $t$, so $-r_t^{\top}w$ is the portfolio loss that day. $T$ is the number of days, $\alpha=0.95$, and $\zeta$ is a free variable. Rockafellar and Uryasev (2000) showed that minimising this expression over both $w$ and $\zeta$ gives the minimum conditional value-at-risk, and that at the optimum $\zeta$ equals the value-at-risk. Only days worse than $\zeta$ contribute, which is why the analytic gradient uses the indicator mask losses > zeta.

The formula

$$n_i=\frac{C_0 w_i}{P_{i,0}},\qquad V_t=\sum_i n_i P_{i,t},\qquad r^{p}_t=\ln\!\left(\frac{V_t}{V_{t-1}}\right),\qquad \text{Calmar}=\frac{\mu^{\text{ann}}_p}{\text{MDD}_p}$$

$C_0$ is the initial capital, $w_i$ the target weight of holding $i$, $P_{i,0}$ its price on the aligned entry date, and $n_i$ the fixed number of shares bought. $V_t$ is the portfolio value on day $t$, $r^p_t$ its log return, $\mu^{\text{ann}}_p$ the annualised portfolio log return and $\text{MDD}_p$ the maximum drawdown of the value path. The Calmar ratio is return per unit of worst-case loss.

Why fixed shares rather than fixed weights

Buy-and-hold means you buy once and do nothing. Weighting the individual asset returns each day would silently rebalance the portfolio back to target every day — a completely different strategy, and one that usually looks better because it sells winners. Converting to share counts on day one and marking those shares to market is the honest version, and it lets the weights drift exactly as they would in a real account.

The point-in-time rule, and the maths behind it

Why a session column cannot simply be joined onto a bar

A session row summarises a whole trading day: its close, its high, its total volume. Joined onto the 10:00 bar of that same day, those columns tell the 10:00 bar what the day is going to do. The join in attach_session_primitives() therefore withholds every column that is not knowable while the session is still running — the whole regular_* summary, the postmarket_* block, and the four next_regular_* columns — 21 columns in total. What survives is backward-looking context: prior_regular_close, prior_regular_range, overnight_gap and the session open.

The formula

Realized volatility of a session, used as the second label one session ahead:

$$\sigma_d=\operatorname{sd}\left(\left\{\ln\frac{p_{i}}{p_{i-1}}\ :\ i\in d\right\}\right), \qquad y^{\text{vol}}_{t}=\sigma_{d(t)+1}$$

The forward return label, attached to every bar of session $d$:

$$y^{\text{ret}}_{t}=\frac{C_{d(t)+1}}{p_t}-1$$

$p_i$ is the close of minute bar $i$; $d$ is one regular session and $i\in d$ runs over its 390 minute bars; $\operatorname{sd}$ is the sample standard deviation; $\sigma_d$ is that session's realized volatility; $d(t)$ is the session containing bar $t$ and $d(t)+1$ is the next session that actually has regular bars, not merely the next row; $C_{d}$ is the regular close of session $d$; $p_t$ is the close of the bar being labelled. Both labels look strictly forward, which is what makes them labels.

17Honest limitations

The selection is in-sample

ETFs are kept because their cumulative return over 2018-2025 cleared a hurdle, and then scored and backtested over that same 2018-2025 window. Every number in section 10 is therefore a fitted value, not a forecast. Nothing in the repository does a walk-forward test, and nothing splits the sample.

Survivorship bias in the universe

The candidate list is built from symbols that traded during 2020-2025 and existed by 2018. ETFs that closed during the window never enter the file at all, so the universe is "funds that made it", not "funds you could have chosen in 2018".

No costs, no taxes, no execution

There are no commissions, no bid-ask spreads, no expense ratios and no tracking error anywhere in the code. For a thirty-holding basket that includes thin funds such as KSA and BIZD, spreads and fund fees are a real drag that the reported Sharpe ratios do not carry.

One covariance estimate, no shrinkage

Every allocation rule uses the plain sample covariance matrix of 2,011 daily observations across 30 assets. That is enough observations to be invertible, but sample covariance is noisy, and max_sharpe in particular is famously sensitive to errors in the mean vector. No shrinkage estimator, no factor model, no bootstrap of the weights.

A single fixed window

HISTORY_START and HISTORY_END are constants. There is no rolling re-selection, no rebalancing, and no sensitivity analysis over the window. The eight years chosen contain one pandemic crash and one bond bear market; a different eight years would produce a different basket, and the code offers no way to see how different.

No single command runs it

The selection method modules have no main(). The only path through the full chain is the notebooks, which means the results depend on execution order and on cell-level constants that are not in any configuration file.

5. Session labels came back all blank on any non-default index — sessionize.py

classify_market_session() builds the session name with np.select, which returns a plain NumPy array with no index. The old code wrapped it as pd.Series(...), so it received a fresh 0..n-1 index. The caller then assigns it to a column of a frame that may have any index at all, and pandas aligns on the index, producing missing values in every row. The two returned series are now built with the caller's index explicitly.

6. A shift over the wrong rows — sessionize.py, labels.py

The trading-date convention in this repository rolls a bar timestamped 20:00 or later onto the next day. A Friday 20:30 bar therefore creates a Saturday session row that holds nothing but overnight bars. The previous-session and next-session columns were built with a plain groupby("symbol").shift(±1) over every row, so that empty Saturday row became Friday's "next session" and Monday's "previous session", and both real values were replaced by missing ones. One shared helper, shift_over_regular_sessions(), now shifts across the rows that have regular bars and reindexes the result back, and it is used by all three places that need it: the four next_regular_* columns, the six prior_regular_* columns, and the next-session realized-volatility label.
